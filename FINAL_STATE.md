# FINAL_STATE.md — зафиксированная рабочая версия (аудит 2026-07-06)

Итог полного аудита автоматизации после недели правок. Дальнейшие изменения
кода вносить ТОЛЬКО при обнаружении реальных багов в проде — не для
доработок или «улучшений ради улучшений».

## 1. Активные точки входа (production)

Два независимых, не связанных друг с другом конвейера. У каждого свой
формат поста, свой источник данных о моделях и своя система дедупа.

### `main_pipeline.py` — лидогенерация по target_models.json
Публикует в @auto_generals компактные посты с ценой «под ключ» и призывом
написать боту. Целевые модели берутся из `target_models.json` (Audi Q3,
VW Tiguan, Kia K3, Kia K5) + широкий поиск по всем моделям с hp≤160.

Активная цепочка модулей:
`main_pipeline.py` → `target_collector.py` + `broad_collector.py` →
адаptеры `kbchachacha_target_adapter.py`, `encar_scraper.py`,
`charancha_scraper.py`, `onbid_scraper.py` → `published_log.py` (дедуп) →
`candidate_diversity.py` (round-robin) → `lead_post_builder.py` →
`post_builder.py` (расчёт цены) → `agent_publisher.py` → `telegram_publisher.py`.

Общие для обоих конвейеров: `config.py`, `model_specs.py`,
`engine_filter.py`, `brand_names_ko.py`, `customs_calculator.py`,
`age_calculator.py`, `rates.py`, `notifier.py`, `target_model_resolver.py`.

Расписание: GitHub Actions `.github/workflows/main_pipeline.yml` —
**сейчас на паузе** (см. раздел 5).

### `main.py` — ценовые алерты по WATCHLIST/USED_CAR_SEARCHES
Публикует в тот же канал алерты «новое поступление» / «цена изменилась» по
жёстко заданному списку в `watchlist.py`. С 2026-07-06 переведён на тот же
компактный формат постов, что и `main_pipeline.py` (через
`price_alert_builder.py` + `price_alert_template.txt`), больше не
использует старый `post_builder.build_telegram_post()` (удалён как мёртвый
код в этом аудите).

Активная цепочка: `main.py` → `scraper.py` / `used_car_scraper.py` →
`database.py` (`cars.db`, отдельный дедуп по цене) →
`price_alert_builder.py` → `post_builder.py` → `agent_publisher.py` →
`telegram_publisher.py`. Если hp не резолвится — молчит и логирует в
`unknown_watchlist_models.json` (не публикует с неточной ценой).

Расписание: GitHub Actions `.github/workflows/run_bot.yml` — **тоже на
паузе** (см. раздел 5).

## 4. Найденные и исправленные реальные баги (2026-07-06)

1. **`mark_posted()` молча ничего не делал**, если URL не был
   заранее зарегистрирован через `select_candidates()` — риск дублей.
   Исправлено: теперь создаёт запись сама, с предупреждением в лог.
2. **`target_collector.py` падал необработанным `KeyError`**, если в
   вручную редактируемом `target_models.json` пропущено поле brand/model —
   ронял ВЕСЬ прогон (и targeted, и broad режимы). Исправлено: битая запись
   пропускается с логом, остальные обрабатываются.
3. **`DEFAULT_RATES` в `customs_calculator.py` были устаревшими** —
   обновлены по 5 подтверждённым живым прогонам на GitHub Actions
   (07-05..07-06): krw_rub=0.04969, eur_rub=88.03, usd_rub=77.23.
   Самотест ЕТС переведён на динамический расчёт ожидаемого значения
   (не ломается визуально при следующем обновлении курса).
4. **3 неиспользуемых импорта** удалены: `config` в `lead_post_builder.py`,
   `dataclass, field` в `customs_calculator.py`, `re` в `encar_scraper.py`.
5. **Мёртвый код удалён**: `post_builder.build_telegram_post()` — не имел
   ни одного вызова в активной цепочке (только упоминания в докстрингах).
6. **`print("═" * 50)` в `telegram_publisher.py` падал с `UnicodeEncodeError`
   на Windows-консоли с кодировкой cp1251** — ЛЮБОЙ `--dry-run` локально на
   этой машине гарантированно падал ещё до показа текста поста. Символ
   `═` заменён на обычный ASCII `=` (косметика, в реальный пост в Telegram
   не попадает).
7. **Текст поста/подписи в `dry_run`-режиме тоже мог упасть с той же
   ошибкой**, если в заголовке остался необработанный корейский текст
   (broad-режим без совпадения с target_models.json). Добавлена
   `_safe_print()` с фолбэком на `errors="replace"` — сам факт публикации
   в Telegram (не dry-run) эта ошибка никогда не затрагивала (JSON API
   всегда кодируется как UTF-8), проблема была только в локальном
   консольном превью.
8. **Критично: `--dry-run` в `main_pipeline.py` навсегда помечал машину как
   опубликованную в `published_log.json`**, хотя реально ничего не
   отправлялось — следующий РЕАЛЬНЫЙ прогон тихо пропустил бы эту машину
   навсегда. Причина: `publish_post(dry_run=True)` всегда возвращает
   `True`, а `mark_posted()` вызывался безусловно при `ok=True`. Исправлено:
   `mark_posted()` теперь вызывается, только если `not args.dry_run`.
   Побочный эффект в `published_log.json` от тестовых прогонов этого
   аудита вручную отменён (URL kbchachacha carSeq=28351887 возвращён к
   состоянию «только first_seen, без posted_at»).

## 5. Известное, но НЕ исправленное в этом аудите (осознанно, вне рамок)

- **У `main.py` есть похожая (более старая, не «этой недели») проблема**:
  `save_car()` в `database.py` коммитит в `cars.db` безусловно, до проверки
  `dry_run` — то есть `--dry-run` для `main.py` тоже может «сжечь»
  легитимный ценовой алерт (следующий реальный прогон увидит цену как
  «unchanged» и промолчит). Не исправлено сейчас: `save_car()` — базовая,
  давно существующая функция (с самого начала проекта), и её сигнатура
  — не баг этой недели. Требует отдельного решения пользователя, стоит ли
  менять сигнатуру `save_car()` ради поддержки dry-run.
- **Пересечение Mercedes GLB между `main_pipeline.py` (broad-режим,
  kbchachacha) и `watchlist.py`/`USED_CAR_SEARCHES` (main.py)** — два
  независимых, не связанных друг с другом дедупа (`published_log.json` vs
  `cars.db`) теоретически МОГУТ увидеть одно и то же объявление и
  опубликовать его дважды разными форматами постов. Вопрос был задан
  пользователю ранее и остался без ответа. 2026-07-06: пользователь явно
  распорядился вернуть оба расписания обратно, несмотря на этот открытый
  риск — см. раздел 7. Если в канале снова появится дубль одного и того
  же объявления в РАЗНЫХ форматах — начинать разбор с этого пункта.
