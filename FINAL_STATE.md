# FINAL_STATE.md — v1.0, финальная стабильная версия (2026-07-06)

Итог полного аудита автоматизации + добавления простого управления
публикацией для нетехнического пользователя. Начиная с этой версии —
дальнейшие изменения кода вносить ТОЛЬКО при обнаружении реальных багов
в проде, не для доработок или «улучшений ради улучшений». Новые каналы
продвижения (VK/Дзен/2ГИС) — отдельными задачами по плану в
**PLAN_NEXT_CHANNELS.md**, не в рамках этой версии.

**Что входит в v1.0:**
- Поиск и расчёт цены по 4 источникам без логина (kbchachacha, Encar,
  Charancha, OnBid), публикация лидогенерирующим постом в Telegram
  (@auto_generals) — см. раздел 1.
- Управление публикацией тремя простыми действиями без правки JSON/YAML
  — см. **CONTROL.md**: `models_to_watch.txt` (простой текстовый список
  моделей, синхронизируется в `target_models.json` автоматически при
  каждом запуске `main_pipeline.py` — см. `models_to_watch.py`),
  `publish_now.py` (публикация конкретной модели прямо сейчас, без
  ожидания расписания — принимает "Марка Модель" и сам ищет/публикует,
  переиспользуя `lead_post_builder.py`), `control.py` (pause/resume/status
  расписания GitHub Actions без ручной правки YAML).
- Все три способа публикации (расписание, `publish_now.py`,
  пауза/возобновление через `control.py`) используют ОДИН и тот же код
  поиска/фильтрации/расчёта цены — не дублируют и не обходят его (см.
  раздел 4, пункты 9-10, и CONTROL.md).

Ничего в существующей архитектуре пайплайнов не менялось — простое
управление добавлено обёрткой поверх неё. Заодно при подготовке живых
примеров нашлись и исправлены 2 реальных бага с ценой — переуступка
аренды на Encar (пункт 9) и стартовая цена аукциона на OnBid (пункт 10).

## 1. Активные точки входа (production)

Два независимых, не связанных друг с другом конвейера. У каждого свой
формат поста, свой источник данных о моделях и своя система дедупа.

### `main_pipeline.py` — лидогенерация по target_models.json
Публикует в @auto_generals компактные посты с ценой «под ключ» и призывом
написать боту. Целевые модели берутся из `target_models.json` (Audi Q3,
VW Tiguan, Kia K3, Kia K5) + широкий поиск по всем моделям с hp≤160.

Активная цепочка модулей:
`main_pipeline.py` → сперва `models_to_watch.py` (перенос простого списка
моделей из `models_to_watch.txt` в `target_models.json`) → затем
`target_collector.py` + `broad_collector.py` → адаптеры
`kbchachacha_target_adapter.py`, `encar_scraper.py`, `charancha_scraper.py`,
`onbid_scraper.py` → `published_log.py` (дедуп) → `candidate_diversity.py`
(round-robin) → `lead_post_builder.py` → `post_builder.py` (расчёт цены) →
`agent_publisher.py` → `telegram_publisher.py`.

**Ручной вход в тот же конвейер:** `publish_now.py "Марка Модель"` —
публикация конкретной модели прямо сейчас, без ожидания расписания.
Использует ТЕ ЖЕ `target_collector.NOLOGIN_TARGET_ADAPTERS` и `lead_post_builder.py`,
что и `main_pipeline.py` — не отдельная, параллельная реализация. См.
CONTROL.md.

Общие для обоих конвейеров: `config.py`, `model_specs.py`,
`engine_filter.py`, `brand_names_ko.py`, `customs_calculator.py`,
`age_calculator.py`, `rates.py`, `notifier.py`, `target_model_resolver.py`.

Расписание: GitHub Actions `.github/workflows/main_pipeline.yml` — каждые
6 часов, активно (см. раздел 7).

### `main.py` — ценовые алерты по WATCHLIST/USED_CAR_SEARCHES
Публикует в тот же канал алерты «новое поступление» / «цена изменилась» по
жёстко заданному списку в `watchlist.py`. С 2026-07-06 переведён на тот же
компактный формат постов, что и `main_pipeline.py` (через
`price_alert_builder.py` + `price_alert_template.txt`), больше не
использует старый `post_builder.build_telegram_post()` (удалён как мёртвый
код в этом аудите).

Активная цепочка: `main.py` → `scraper.py` / `used_car_scraper.py` →
`database.py` (`cars.db`, отдельный дедуп по цене) →
`price_alert_builder.py` → `post_builder.py` → `agent_publisher.py` →
`telegram_publisher.py`. Если hp не резолвится — молчит и логирует в
`unknown_watchlist_models.json` (не публикует с неточной ценой).

Расписание: GitHub Actions `.github/workflows/run_bot.yml` — каждые 6
часов, активно (см. раздел 7).

## 4. Найденные и исправленные реальные баги (2026-07-06)

1. **`mark_posted()` молча ничего не делал**, если URL не был
   заранее зарегистрирован через `select_candidates()` — риск дублей.
   Исправлено: теперь создаёт запись сама, с предупреждением в лог.
2. **`target_collector.py` падал необработанным `KeyError`**, если в
   вручную редактируемом `target_models.json` пропущено поле brand/model —
   ронял ВЕСЬ прогон (и targeted, и broad режимы). Исправлено: битая запись
   пропускается с логом, остальные обрабатываются.
3. **`DEFAULT_RATES` в `customs_calculator.py` были устаревшими** —
   обновлены по 5 подтверждённым живым прогонам на GitHub Actions
   (07-05..07-06): krw_rub=0.04969, eur_rub=88.03, usd_rub=77.23.
   Самотест ЕТС переведён на динамический расчёт ожидаемого значения
   (не ломается визуально при следующем обновлении курса).
4. **3 неиспользуемых импорта** удалены: `config` в `lead_post_builder.py`,
   `dataclass, field` в `customs_calculator.py`, `re` в `encar_scraper.py`.
5. **Мёртвый код удалён**: `post_builder.build_telegram_post()` — не имел
   ни одного вызова в активной цепочке (только упоминания в докстрингах).
6. **`print("═" * 50)` в `telegram_publisher.py` падал с `UnicodeEncodeError`
   на Windows-консоли с кодировкой cp1251** — ЛЮБОЙ `--dry-run` локально на
   этой машине гарантированно падал ещё до показа текста поста. Символ
   `═` заменён на обычный ASCII `=` (косметика, в реальный пост в Telegram
   не попадает).
7. **Текст поста/подписи в `dry_run`-режиме тоже мог упасть с той же
   ошибкой**, если в заголовке остался необработанный корейский текст
   (broad-режим без совпадения с target_models.json). Добавлена
   `_safe_print()` с фолбэком на `errors="replace"` — сам факт публикации
   в Telegram (не dry-run) эта ошибка никогда не затрагивала (JSON API
   всегда кодируется как UTF-8), проблема была только в локальном
   консольном превью.
8. **Критично: `--dry-run` в `main_pipeline.py` навсегда помечал машину как
   опубликованную в `published_log.json`**, хотя реально ничего не
   отправлялось — следующий РЕАЛЬНЫЙ прогон тихо пропустил бы эту машину
   навсегда. Причина: `publish_post(dry_run=True)` всегда возвращает
   `True`, а `mark_posted()` вызывался безусловно при `ok=True`. Исправлено:
   `mark_posted()` теперь вызывается, только если `not args.dry_run`.
   Побочный эффект в `published_log.json` от тестовых прогонов этого
   аудита вручную отменён (URL kbchachacha carSeq=28351887 возвращён к
   состоянию «только first_seen, без posted_at»).
9. **`encar_scraper.py` публиковал переуступку аренды как обычную продажу**
   (найдено 2026-07-06 при подготовке живого примера для CONTROL.md):
   некоторые объявления на Encar — не продажа машины, а переуступка
   договора аренды (`advertisementType: "RENT_SUCCESSION"`); для них поле
   `item["Price"]`, которое наш код принимал за цену автомобиля, на самом
   деле — сумма переуступки (в разы меньше рыночной цены), что давало
   абсурдно заниженную «цену под ключ» в посте. Признак виден уже в
   списке объявлений (`item["SellType"]`: `"일반"` обычная продажа vs
   `"렌트"` аренда — подтверждено вживую), фильтр не проверял его вообще.
   Исправлено: добавлен allow-list фильтр (`SellType == "일반"`) в обоих
   местах сбора (`search_target_model()` и `browse_broad()`). Charancha
   проверена отдельно (выборка 100 объявлений, все `saleType: "CASH"` —
   аномалий не найдено); kbchachacha проверить не удалось (антибот-защита
   сайта заблокировала прямой запрос) — см. раздел 5.
   Также найдена смежная проблема при добавлении Hyundai Sonata: одна и
   та же спецификация в `model_specs.py` случайно матчила и бензиновые, и
   гибридные (HEV) варианты с одинаковым текстом трима — спецификация
   Sonata удалена (не добавлена без точных данных по гибриду), модель
   убрана из `target_models.json`/`models_to_watch.txt`.
10. **`onbid_scraper.py` использует стартовую цену аукциона
    (`item["lowstBidPrc"]`) как «цену автомобиля»** — для гос. площадки
    аукционов это НЕ гарантированная цена покупки (итоговая цена по факту
    торгов может быть выше). По решению пользователя — не исключать OnBid
    и не подменять цену оценочной стоимостью, а честно пометить в самом
    посте. Добавлен плейсхолдер `{price_label}` в `lead_post_template.txt`
    и `lead_post_builder.py`: для `car["source"] == "onbid"` строка цены
    показывает «Стартовая цена аукциона под ключ в Казани (итоговая может
    быть выше)» вместо обычной «Стоимость под ключ в Казани». Для всех
    остальных источников текст поста не изменился.
11. **КРИТИЧНО: `encar_scraper.py` и `charancha_scraper.py` использовали
    корейский маркетинговый «модельный год» вместо реальной даты
    производства для расчёта таможенного возраста** (найдено 2026-07-06 на
    реальном примере Chevrolet Trax — машина реально произведена в апреле
    2023, но `item["FormYear"]` показывало "2024", т.к. в Корее машины,
    произведённые во 2-й половине года, почти всегда маркируются модельным
    годом следующего года). Возраст считался как 2 года (категория "u3",
    до 3 лет) вместо правильных 3 года (категория "35", 3-5 лет) — ЕТС и
    утильсбор по неверной ставке, итоговая цена в уже опубликованном посте
    (2 316 527 ₽) завышена на 415 048 ₽ относительно корректного расчёта
    (1 901 478,80 ₽). Проверено на выборке Charancha — расхождение между
    маркетинговым годом и реальной датой встретилось в 51 из 100 объявлений
    (больше половины!) — баг был системным, затрагивал большинство постов
    через эти 2 источника, не только этот один случай.
    Исправлено: `encar_scraper.py` теперь берёт год из `item["Year"]`
    (формат ГГГГММ, реальная дата) вместо `item["FormYear"]` (маркетинговый
    год); `charancha_scraper.py` — из `item["firstRegisteredAt"]` вместо
    `item["releaseYear"]`. Оба — с фолбэком на старое поле, если новое
    отсутствует. `kbchachacha` (`used_car_scraper.py`) проверен — уже был
    корректен изначально (парсит дату ДО скобки в "22/11식(22년형)", а не
    маркетинговый год из скобок). `onbid_scraper.py` — НЕ проверен (см.
    раздел 5), но источник почти никогда не находит кандидатов на практике.
    По решению пользователя — уже опубликованный пост с завышенной ценой
    НЕ удалён и не исправлен, оставлен как есть.
12. **СРОЧНО, найдено в проде: broad-режим (модели без совпадения в
    target_models.json) публиковал заголовок поста сырым корейским текстом
    с сайта** вместо человекочитаемого названия (напр. "기아 더 뉴 기아 레이
    1.0 가솔린 시그니처" вместо "Kia Ray 1.0 Gasoline"). Реальный прогон
    2026-07-06 18:19 UTC — ВСЕ 5 постов вышли с этим багом (Hyundai Casper,
    Kia Ray ×3, Hyundai Avante Hybrid). Причина: `find_spec()` уже находит
    подходящую запись в `model_specs.py` (иначе `hp` был бы `None`, и
    машина отсеялась бы фильтром до публикации) — то есть каноническое имя
    (`spec.label`, напр. "Kia Ray 1.0 Gasoline") уже было доступно, но не
    использовалось, а car["model"] оставался сырым текстом с сайта. Баг
    был в 3 из 4 источников: `used_car_scraper.py`/`kbchachacha_target_adapter.py`
    (title целиком не переведён), `onbid_scraper.py` (та же схема, её
    собственный docstring прямо ссылался на приём kbchachacha), и
    `encar_scraper.py` (`from_korean()` переводил только БРЕНД — сама
    МОДЕЛЬ, напр. "쏘나타 디 엣지(DN8)", оставалась корейской). Charancha —
    на тот момент НЕ проверена (её `modelName`/`modelDetailName` — отдельные
    структурированные поля, обычно уже латиницей, но не гарантированно
    всегда — см. пункт 13, баг подтвердился и там).
    Исправлено во всех трёх: если `find_spec()` нашёл совпадение —
    `model` = `spec.label`, `brand`/`trim` очищаются (иначе марка
    дублируется: "Hyundai" + "Hyundai Sonata..."). Если совпадения нет —
    поведение не изменилось (car и так отсеивается фильтром `hp is None`
    до публикации, так что "нет спека — нет поста" было и остаётся).
    Проверено на всех 5 реальных названиях из бракованного прогона — все
    корректно резолвятся в человекочитаемые имена.

    (`post_validator.py`: фото ≥3, регекс на хангыль в названии, год в

    @auto_generals без фото и с корейским текстом в названии 2026-07-06
    10:04 (`logs/app.log`, закоммичен) и повторно 2026-07-07 — `git diff`
    подтвердил, что `post_validator.py` был untracked, а `HEAD:main.py` не
    содержал ни одной ссылки на него. Архитектурный фикс: гейт перенесён
    ВНУТРЬ `agent_publisher.publish_post()` — единственной функции, которая
    реально вызывает `send_to_telegram`/`send_to_vk` (проверено grep — других

    GitHub Actions (`main_pipeline.yml`/`run_bot.yml`) теперь фейлит job
    (`exit 1`), если `rejected_posts.log` не пуст после прогона.

## 5. Известное, но НЕ исправленное в этом аудите (осознанно, вне рамок)

- **У `main.py` есть похожая (более старая, не «этой недели») проблема**:
  `save_car()` в `database.py` коммитит в `cars.db` безусловно, до проверки
  `dry_run` — то есть `--dry-run` для `main.py` тоже может «сжечь»
  легитимный ценовой алерт (следующий реальный прогон увидит цену как
  «unchanged» и промолчит). Не исправлено сейчас: `save_car()` — базовая,
  давно существующая функция (с самого начала проекта), и её сигнатура
  — не баг этой недели. Требует отдельного решения пользователя, стоит ли
